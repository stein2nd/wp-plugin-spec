# wp-plugin-spec - 管理画面、フロント UI と画面遷移 (ひな型)

* 各プラグインリポジトリ直下の `docs/` フォルダー等にコピーして利用することを想定する。
* コピー後、1行目を `# <plugin-slug> - 管理画面、フロント UI と画面遷移` に変更すること。
* ファイル名の一例: `docs/SPEC_UI_AND_FLOWS.md`

* **目的**:
  * 「管理画面の仕様」「Gutenberg ブロック仕様」「Classic エディター対応」を **プラグイン固有の画面設計に落とし込む**。
* **内容例**:
  * 管理画面のワイヤーフレーム／コンポーネント一覧
  * 各画面の入力項目・バリデーション・エラーメッセージ
  * ブロックの属性一覧と編集 UI の挙動
  * ユーザーフロー (例: 設定〜保存〜プレビュー〜公開)
* **AI 的メリット**:
  * React/TypeScript コンポーネントを生成するときに、**画面単位の仕様をそのままプロンプト化しやすい**。

React コンポーネントは、UI アダプタです。バリデーションと判断は、`src/` 配下の純関数 (`utils/` 等) に置き、コンポーネントに混ぜません。Settings API とメニュー登録は、PHP アダプタ (`includes/`) が行います。

## 1. スタイル規約

* 余白・間隔 (padding, margin, blockGap 等)、テキストサイズ を rem で定義すること
* WordPress コアの慣例に準拠し、`rem` を基本単位とする。
* `px` は微調整や境界条件に限って利用する。
* `em` はコンポーネント内部の相対サイズ調整に限定する。
* 利用可能なプロパティの詳細は `docs/SPECS.md` のスタイル規約を参照する。

## 2. 画面仕様 (UI) とフロー

管理画面は、下記に準拠します。ここは、アダプタです。

* 設定ページは、`add_options_page` または `add_menu_page` を利用する。
* 設定値の読み書きは、`register_setting` / `get_option` / `update_option` をアダプタで行う。ドメイン関数は、option 名を直接呼ばない。
* API キー等は、WordPress Options API に保存する。
* セキュリティ上の理由から、必ず `sanitize_callback` を設定する。Nonce と capability もアダプタで行う。
* 画面上のエラーは、notice またはフォームメッセージで出す。空の `catch` にしない。

## 3. Gutenberg ブロック UI (該当する場合)

Gutenberg ブロックは、下記に準拠します。編集 UI は、アダプタ、属性の正規化は、純関数に出します。

* [ブロックエディターハンドブック](https://ja.wordpress.org/team/handbook/block-editor/) に準拠する。
* ブロックは `src/` に実装し、`register_block_type` で `dist/` 出力物を読み込む (登録は PHP アダプタ)。
* `edit` 側は React Hooks を利用。
* 翻訳文字列は `@wordpress/i18n` を利用 (`__()`, `_x()`)。
* `save` は必要に応じて実装するが、REST 経由の処理が多いため `null` 戻りが基本。
* Gutenberg 用ブロックは `block.json` を正とし、編集画面・保存処理の双方で仕様を満たすこと。

## 4. AI 伴走開発での使い方メモ

* **UI 実装タスク**:
  * 本ファイルの「2. 画面仕様 (UI) とフロー」を AI に渡し、対象画面 ID を明示してコンポーネント生成を依頼する。
  * 判断は `utils/` の純関数へ出すこと、コンポーネントにドメイン判断を混ぜないことを前提に含める。
* **ブロック実装タスク**:
  * 「3. Gutenberg ブロック UI」の対象ブロックを指定し、`src/gutenberg/` 配下の実装を依頼する。
* 参照させる関連仕様:
  * `SPEC_ARCHITECTURE.md` (アダプタとドメインの境界)
  * `SPEC_DATA_DICTIONARY.md` (保存先の option/meta 定義)
