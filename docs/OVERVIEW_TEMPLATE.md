# wp-plugin-spec - プロジェクトの存在理由 (ひな型)

* 各プラグインリポジトリ直下の `docs/` フォルダー等にコピーして利用することを想定する。
* コピー後、1行目を `# <plugin-slug> - プロジェクトの存在理由` に変更すること。
* ファイル名の一例: `docs/SPEC_OVERVIEW.md`

* **目的**:
  * プラグインの「存在理由」「解決したいユーザー課題」「スコープ/非スコープ」を明文化する。
* **AI 的メリット**:
  * 「このプラグインは何のためのものか ?」を毎回説明せずに済む。
  * 仕様追加時に「スコープ外」を AI に判定させやすくなる。

設計方針 (ドメインは純関数、I/O はアダプタ) は、`docs/SPECS.md` の「2. 設計方針」を正とします。本ファイルには、プラグイン固有の Why / 環境を書きます。

### 2.1. 主な機能一覧

ユースケースは、REST エンドポイント、フック、管理画面の操作、任意の WP-CLI として書きます。サブコマンドという語は使いません。

```text
* 機能1:

```

### 2.2. 成功指標 (KPI/採用基準)

* 導入サイト数や有効インストール数など、可能であれば数値目標を書く
* ユーザー体験の指標 (例: 設定完了までのクリック数、1画面あたりの入力項目数)

## 3. 想定環境・前提条件

本章では、「開発に必要な技術情報」を記載します。

* 対応 WordPress バージョン: たとえば、「WordPress 6.x 系を対象」
* 対応 PHP バージョン:
* 対応 Node.js バージョン: たとえば、「v18以降」
* 対応 npm バージョン: たとえば、「v9以降」
* ローカル開発は「Local by Flywheel」または同等の環境を利用すること
* 必須となる他プラグイン/テーマとの依存関係: あれば明記。連携は Composer より先に、存在チェックとフックで行う

### 3.1. フロントエンド技術スタック

* **React v18.2**:
  * 管理画面 UI の構築 (UI アダプタ。実行時は WordPress 提供の React)
* **TypeScript v5.9**:
  * 型安全性の確保
* **SCSS**:
  * スタイル管理とデザインシステム
* **Vite v7.1**:
  * 高速ビルドとモジュールバンドリング

### 3.2. ビルド要件

* Vite + TypeScript + SCSS
  * `vite.config.ts` を用いて IIFE 形式でバンドルする
  * JavaScript は WordPress 同梱の jQuery を利用可能とする (外部 import 不要) (`jQuery(function($) { ... })`)
  * CSS も IIFE 出力し、エディター用・フロント用を区別すること
* 出力は `./dist` (Git 管理外。リリース時に Zip へ同梱)

### 3.3. `package.json` の `scripts`

サードパーティは、npm または Composer 経由で導入します。WordPress 本体と `@wordpress/*` は対象外です。

* `npm run build:dev` → 開発用ビルド (minify 無効)
* `npm run build:production` → 本番用ビルド (minify 有効)
* `npm run dev` → 開発用ビルド (watch モード)
* `npm run lint` → ESLint + Stylelint によるコード品質チェック
* `npm run makepot` → 翻訳テンプレート生成

## 5. AI 伴走開発の観点メモ (任意)

* このプラグインで AI に特に気を付けてほしい点:
  * 例として、「文言は必ず i18n 関数を通すこと」「セキュリティチェックを絶対にスキップしないこと」「判断は純関数、WordPress API はアダプタへ」
* AI に渡すときに必ず一緒に読ませたいドキュメント:
  * `SPECS.md` (設計方針を含む)

  * `SPEC_DATA_DICTIONARY.md` など
